## 1. Problem Statement (SIH26176)

This project is being built for Smart India Hackathon, Problem Statement
26176, sponsored by ISRO (Indian Space Research Organisation), under the
**Disaster Management** theme.

**Title:** ORCA — Marine EcOsystem Reasoning with Collaborative Agents

**Background:** The marine ecosystem plays a vital role in supporting
livelihoods, food security, biodiversity, maritime transportation, coastal
resilience, and the blue economy. Every day, vast volumes of satellite Earth
Observation and oceanographic data (Sea Surface Temperature, chlorophyll
concentration, weather forecasts) are generated by ISRO and other global
agencies. Marine stakeholders (fishermen, researchers, coastal authorities,
disaster management agencies, maritime operators) need timely access to this
information. Advances in Agentic AI, conversational intelligence, and
geospatial technologies present an opportunity to transform how marine
information is accessed.

**Description:** Develop an Agentic AI-powered conversational platform that
lets users access, analyze, and reason over marine information using natural
language. The platform should autonomously interpret user intent, decompose
complex requests into executable tasks, coordinate multiple specialized AI
agents, retrieve relevant marine/geospatial datasets, perform spatial-temporal
reasoning, and synthesize actionable recommendations conversationally.

**Typical user queries the platform must answer:**
- Where is the nearest Potential Fishing Zone (PFZ) today?
- Is it safe to venture into the sea tomorrow morning?
- What are the tide, weather, and sea conditions near my fishing location?
- Are there any lightning or cyclone alerts in my area?
- Which regions show high chlorophyll and favourable SST?
- What is the safest route for a fishing vessel given weather/sea-state?
- Why has fish productivity declined in a particular coastal region?
- Which fishing zones should be avoided due to hazardous conditions or
  geofencing restrictions?

**Expected Solution capabilities (from the official PS):**
- Natural language understanding, multi-turn conversation
- Automatic language identification, responding in the same language
  (emphasis on Indian regional languages)
- Autonomous discovery/retrieval/integration of satellite, marine,
  meteorological, geospatial datasets
- Spatial, temporal, contextual reasoning correlating heterogeneous sources
- Explainable, evidence-based recommendations with maps/charts/visualizations
- Proactive alerts for adverse weather, high waves, lightning, cyclones
- Geofencing notifications near international maritime boundaries,
  restricted waters, marine protected areas
- Route optimization / safe navigation / operational planning
- A modular multi-agent architecture: planning, marine data discovery,
  weather intelligence, ocean analytics, geospatial reasoning, risk
  assessment, visualization, reporting, user interaction agents

## 2. What ORCA Actually Is (Current State)

A working FastAPI + LangGraph backend, with a vanilla HTML/CSS/JS frontend
(a React rebuild is planned but not yet started — see Section 11), that:

1. Takes a natural-language query (typed or spoken) in English, Hindi, or
   Marathi
2. Detects which of 4 stakeholder types is asking (fisherman, coast_guard,
   disaster_management, general) via deterministic keyword scoring
3. Resolves the location (25 known coastal cities with native-script
   aliases, or ANY other city via live geocoding + a coastal-proximity
   sanity check)
4. Fetches LIVE wind, wave, and lightning data (Open-Meteo, free, no API
   key) — with automatic fallback to generic mock values if the live call
   fails
5. Computes 4 individual risk metrics (Wave/Wind/Cyclone/Lightning, each
   0-100) via a **deterministic Risk Engine** — never LLM-generated numbers
6. Combines those into a stakeholder-weighted overall score (0-100) and
   LOW/MODERATE/HIGH/CRITICAL level — different stakeholders get different
   weightings on the SAME underlying conditions
7. If the query is a route request ("find the safest route from X to the
   fishing zone"), generates 3 candidate routes, samples environmental
   conditions along each, scores them via the SAME Risk Engine, and
   recommends the safest one (not necessarily the shortest)
8. Renders a live risk heatmap across all 25 known coastal zones on a
   Leaflet map
9. Uses Gemini (google-generativeai, model `gemini-3.6-flash`) to explain
   the computed numbers in natural language, in the detected language —
   with a fully deterministic multilingual fallback template if Gemini is
   unavailable, rate-limited, or times out
10. Speaks the answer aloud (Web Speech API `speechSynthesis`) in the
    correct language, and accepts spoken input (`SpeechRecognition`)

## 4. Data: What's REAL (Live) vs MOCK — Be Precise About This

This distinction is central to the project's honesty and to the PS's own
data-source requirements. **Never blur this line in code or in the pitch.**

| Field | Status | Source |
|---|---|---|
| Wind speed, precipitation | **LIVE** | Open-Meteo Forecast API (free, no key) |
| Wave height | **LIVE** | Open-Meteo Marine API (free, no key) |
| Lightning alert | **LIVE-DERIVED** | Inferred from Open-Meteo's WMO weather code (95/96/99 = thunderstorm) |
| Sea surface temperature | **LIVE** (MOSDAC Ocean-Eye preferred; else Open-Meteo; else mock default 28.0°C) | MOSDAC Ocean-Eye WMS (`SAC_OSF_CIRC_10KM.nc`, `temp` layer) |
| Salinity | **LIVE**, `null` if MOSDAC unreachable (no mock fallback) | MOSDAC Ocean-Eye WMS (`salinity` layer, psu) |
| Ocean current speed | **LIVE**, `null` if MOSDAC unreachable (no mock fallback) | MOSDAC Ocean-Eye WMS (vector sum of `eastward_ocean_wave_current` + `northward_ocean_wave_current`, converted cm/s → m/s) |
| Mixed layer depth | **LIVE**, `null` if MOSDAC unreachable (no mock fallback) | MOSDAC Ocean-Eye WMS (`hmxl` layer, converted cm → m) |
| Chlorophyll | **MOCK** (only for 3 "rich" demo cities; `null` for the other 22 + geocoded cities) | No free live API exists for this |
| Cyclone alert | **MOCK** (only Chennai currently has one, `cyclone_alert: true`, for demo purposes) | No free live cyclone-tracking API exists |
| Potential Fishing Zone (PFZ) location | **MOCK** (only for the 3 "rich" demo cities: Kochi, Chennai, Visakhapatnam; `null` for the other 22 + geocoded cities) | INCOIS has NO public API — confirmed via research. Only web bulletins/WebGIS exist, not programmatically accessible |

**Wave height stays on Open-Meteo deliberately, not MOSDAC**: MOSDAC does
publish its own wave product (`SAC_OSF_WAVE_10KM.nc`), but it was checked
in this session and found STUCK/STALE (data only up to 2026-04-26, ~5
months old) — see Section 14f for the full investigation. Do not switch
wave height to MOSDAC without re-checking that file's freshness first.

**The 3 "rich" demo cities** (Kochi, Chennai, Visakhapatnam) have full mock
data (chlorophyll + cyclone + PFZ). **The other 22 cities** in
`marine_data.json` only have real coordinates — everything else is `null`,
and the system HONESTLY says "no PFZ advisory available" rather than
inventing one. **Any other city not in the JSON at all** gets resolved via
live geocoding (Open-Meteo Geocoding API) + a coastal-proximity check
(`is_near_coast`, rejects landlocked results like "Kashmir").

**Day offset / forecast date**: the system correctly parses "today" /
"tomorrow" / "N days later" (English, Hindi, Marathi) and fetches an actual
FORECAST for that day, not just "right now" — this was a real bug we found
and fixed (see Section 8).

## 5. Key Design Decisions — the "WHY", not just the "WHAT"

These are decisions that look arbitrary in the code but were made
deliberately, after discussion. **Do not "simplify" or "fix" these without
understanding why they're this way first.**

1. **Deterministic-first, LLM-explains-only.** The Risk Engine
   (`core/risk_engine.py`) computes every number. Gemini's ONLY job in
   `synthesis.py` is to explain those numbers in natural language — the
   prompt explicitly forbids inventing/changing scores or claiming a
   hazard exists when its metric is 0. This is directly required by the
   spec ("LLM must NOT invent route-risk values").

2. **Fallback-everywhere is load-bearing, not optional polish.** Every
   external call has a graceful degradation path:
   - Live weather/wave fails → generic mock defaults
   - Gemini fails/times out/rate-limited → deterministic multilingual
     template answer (`_build_fallback_answer` in synthesis.py)
   - Geocoding fails → honest "couldn't identify location" error
   This pattern has saved the demo MANY times during development (Gemini's
   free tier rate limits and 30-60s latency spikes were a recurring real
   problem). **Never remove a fallback path to "clean up" code.**

3. **Route risk = MAX of sample scores, not average.** A route is only as
   safe as its most hazardous point along the path, not its average
   condition. This is in `route_engine.py`'s `score_route()`.

4. **Route selection is NOT "shortest wins."** `select_recommended_route()`
   combines risk score with a distance penalty (2 points per extra km
   relative to the shortest candidate) — a longer route can win if it's
   meaningfully safer. This exact weighting was validated against the
   spec's own worked example (17km/risk78 vs 21km/risk24 → 21km route
   correctly wins).

5. **Cyclone risk is binary (0 or 100), never in-between.** There's no free
   live cyclone intensity/tracking API, so rather than inventing a
   plausible-looking intermediate number, the system only ever says
   "active alert" (from mock data) or "no active alert" — no fabricated
   nuance.

6. **Stakeholder-specific weighting genuinely changes outcomes**, not just
   labels. `STAKEHOLDER_WEIGHTS` in `risk_engine.py` — fisherman leans
   wave/wind/cyclone, disaster_management leans cyclone/regional hazard,
   coast_guard is balanced. This was proven to matter: a high-wave/no-cyclone
   scenario landed disaster_management at LOW while everyone else got
   MODERATE — a genuinely different classification, not cosmetic.

7. **Stakeholder detection is keyword-based, not an LLM call.** Deliberately
   deterministic (free, instant, doesn't compete with Gemini's rate limit).
   Same for route-request detection.

8. **PFZ reuse for route destinations.** When a route request mentions "the
   fishing zone" / PFZ, the destination is the ALREADY-KNOWN `nearest_pfz`
   from `marine_data.json` for the resolved origin city — never a second,
   separate data source. If no PFZ exists for that city, the route request
   fails gracefully with an honest message, per the spec's explicit "do
   not invent coordinates" rule.

## 6. Known Bug Classes — Patterns to Watch For

These bugs were each found and fixed once already. **Watch for these exact
patterns recurring**, especially the LangGraph ones, since they're subtle.

### 6a. LangGraph "must write to at least one key"
A node CANNOT return an empty dict `{}`, even when it has nothing to
contribute (e.g., short-circuiting on an error). Every node must return
`{"some_key": None}` — writing `None` to its OWN unique key — never `{}`.

### 6b. LangGraph depth-synchronization race condition (hit 3 times)
If two parallel branches feed into a shared downstream "barrier" node, and
those branches are at DIFFERENT depths from a common ancestor (one is 1 hop
away, the other is 2 hops away), the barrier node can fire prematurely —
before the deeper branch has finished — causing a `KeyError` on missing
state. **The fix is always the same: restructure the graph so every branch
feeding a shared barrier node is at the exact same depth.** Look at
`workflow.py`'s comments for the current correct topology
(`route_planning_node` specifically had to be re-routed through
`route_detection_node` rather than being a direct sibling, for exactly
this reason).

### 6c. LangGraph concurrent-write conflict
Two parallel nodes writing to the SAME state key in the same step raises an
error, even if the values are identical. Fix: never use
`return {**state, "new_key": value}` in a node that might run in parallel
with others — only return the NEW key(s) that specific node is adding.

### 6d. Python `from X import Y` creates a separate binding
If module `weather.py` does `from app.services.weather_api import
fetch_live_wind`, then mocking `app.services.weather_api.fetch_live_wind`
in a test will NOT affect what `weather.py` actually calls — you must
patch `app.graph.agents.weather.fetch_live_wind` (the importing module),
not the source module. See `tests/test_phase7.py` Test 4 for the correct
pattern.

### 6e. Regex without word boundaries
A location-extraction regex looking for "at X" matched the "at" inside
"wh**at** about mumbai", extracting the wrong word. Fixed with `\b`
boundaries. **Always use word boundaries in location/keyword regexes.**

### 6f. Fuzzy geocoding can return wildly wrong results
Open-Meteo's geocoding does fuzzy text search, not exact matching —
nonsense input like "hii" once matched a real place called "Lake Havasu
City". Fixed with a prefix-match sanity check (`geocode_location()` in
`geocoding.py`) rejecting results where the first few letters don't match
the input.

### 6g. File casing on case-sensitive filesystems
`Script.js`/`Style.css` (capitalized) vs `index.html` referencing lowercase
`script.js`/`style.css` — silently worked on macOS (case-insensitive) but
would 404 on Linux. **Always use lowercase filenames consistently.**

### 6h. Mock coordinate drift
Visakhapatnam's PFZ coordinate was originally offset both north AND east
from the city, which (given the coastline's actual curve there) placed it
very close to/on land when drawn precisely on a map. Fixed by using a
same-latitude, due-east offset instead — a more reliable heuristic for
staying in open water on an east-facing coast. **Any new mock coordinate
should be sanity-checked by actually drawing it on a map, not just
eyeballing the lat/lon numbers.**

## 7. Testing Philosophy (established over the whole project)

- **Never trust "it should work" — always execute it.** Every feature in
  this project was verified by actually running it (real function calls,
  real FastAPI TestClient requests, or realistic mocked data), not just
  code review.
- **For JS, browsers share top-level `const`/`let` across separate
  `<script>` tags — Node's `eval()` does NOT.** When testing multiple JS
  files together outside a real browser, concatenate them into one string
  and `eval()` that as a single unit, matching real browser semantics,
  rather than `eval()`-ing each file separately in a loop.
- **When mocking a live API failure, actually simulate the failure mode**
  you're protecting against (e.g., a promise that never resolves for a
  "hang" test, not just a rejected promise — those are different failure
  modes requiring different protections).
- Run `python3 -m tests.test_phase7` after ANY change to confirm the 6
  core scenarios (fisherman/coast_guard/disaster_management/high-risk
  fisherman/Hindi/Marathi) still pass — this is the fastest regression
  check available.

## 9. Current API Contract

### `GET /`
Health check. Returns `{"status": "ORCA backend is running"}`.

### `GET /zones?stakeholder=<type>`
Returns risk for all 25 known coastal zones, computed in parallel via a
thread pool (25 zones × 2 live API calls each = 50 calls; sequential would
be too slow). `stakeholder` defaults to `"general"`.
```json
{
  "zones": [
    {"name": "Kochi", "lat": ..., "lon": ..., "overall_score": 19,
     "overall_level": "LOW", "primary_driver": "Wave Risk",
     "wave_height_m": ..., "wind_speed_kmph": ..., "recommendation": "...",
     "data_source": "live", "has_data": true}
  ],
  "legend": {"LOW": "🟢", "MODERATE": "🟡", "HIGH": "🟠", "CRITICAL": "🔴"}
}
```

### `POST /ask`
Body: `{"query": "..."}`. Response (success case):
```json
{
  "answer": "...",
  "language": "en",
  "risk_level": "safe",              // legacy field, kept for compatibility
  "risk_reasons": ["..."],           // legacy field
  "weather": {...}, "ocean": {...},
  "map": {"user_location": {...}, "location_name": "...", "nearest_pfz": {...} or null},
  "stakeholder": {"type": "fisherman", "confidence": 0.85},
  "risk": {
    "overall_score": 19, "overall_level": "LOW",
    "metrics": [{"name": "Wave Risk", "key": "wave_risk", "score": 45}, ...],
    "reasons": [{"factor": "Wave", "score": 45, "reason": "..."}],
    "recommendation": "...",
    // --- Section 14n: government/hard-safety override layer, additive ---
    "pre_override_level": "LOW",     // what the weighted calculation alone produced
    "override_fired": false,         // true if a hard-safety rule matched (see Section 14n)

  "policy_answer": null,  // or {is_policy_answer, answer, mode, sources} - see Section 14h

}
```
On error (`result.get("error")` truthy — e.g., unresolvable location):

## 13. RESEARCH FINDINGS: MOSDAC + Maritime Boundary Data (verified via direct web fetch)

### 14a. MOSDAC Data Download API — genuinely more complex than a simple REST API

**Verified directly from MOSDAC's own published user manual**
(mosdac.gov.in/downloadapi-manual). Key facts:

- It is a **file-download tool**, not a point-query API like Open-Meteo.
  You provide a `config.json` with a `datasetId` (e.g., `"3SIMG_L1B_STD"`,
  found by browsing mosdac.gov.in/catalog-app/satellite), an optional
  `boundingBox` (format: `"minLon,minLat,maxLon,maxLat"`), date range,
  and count — then run `python mdapi.py`, which downloads matching
  **satellite scene files** (likely NetCDF/HDF5 format, based on typical
  ISRO satellite product formats — not directly confirmed in the manual,
  needs checking once a specific product is chosen).
- **This means getting a single SST or chlorophyll VALUE at one lat/lon
  point requires: (1) finding the right datasetId for that product,
  (2) downloading a full scene file covering that area, (3) parsing that
  file with something like `xarray`/`h5py`/`netCDF4` to extract the pixel
  value at your specific coordinate.** This is a real geospatial data
  engineering task, not a quick API call — realistically 1-2+ days of
  work just to get ONE working extraction pipeline, even before dealing
  with real-time freshness (satellite revisit time, file availability
  lag).
- **Authentication**: searching/browsing datasets needs NO login; only
  actual file DOWNLOAD requires a MOSDAC account. Register at
  mosdac.gov.in/signup/ — approval is required before downloading (this
  is why registering EARLY, on Day 1-2, matters).
- **Quotas**: 5000 files/day/user (not a bottleneck for a demo). 3 failed
  logins in a row = 1 hour account lockout (be careful with credentials
  in scripts/config files during testing).
- Relevant ocean product categories that exist on MOSDAC's Open Data page
  (confirmed real, though exact datasetIds need to be looked up in their
  catalog): Global Ocean Surface Current, High Resolution Sea Surface
  Salinity, Indian Mainland Coastal Product, Ocean Subsurface, Oceanic
  Eddies Detection, Wave based Renewable Energy.

**Recommendation for the 10-day plan**: attempt this with a **strict
1-day time-box**. If a working point-value extraction isn't functioning
by the end of Day 3, STOP and use NASA Ocean Color
(oceancolor.gsfc.nasa.gov) or Copernicus Marine
(data.marine.copernicus.eu) instead — both are still genuinely real,
public, free ocean data sources (just not ISRO-branded), and both
generally offer more developer-friendly access than a raw satellite-file
archive. A working non-ISRO real data source beats a broken or
half-finished ISRO one. Be honest in the pitch either way about exactly
which parts are ISRO-sourced vs. not.

### 14b. Maritime boundary / geofencing data — actually LOWER risk than assumed

**Good news, verified via direct research**: getting real, usable
maritime boundary data is much easier than the MOSDAC situation.

- **Marine Regions** (marineregions.org), maintained by VLIZ (Flanders
  Marine Institute) in partnership with IOC-UNESCO, is the standard
  authoritative source for Exclusive Economic Zone (EEZ) boundaries
  worldwide. **All data is free, open-licensed, and downloadable** as
  Shapefile, GeoJSON, GeoPackage, or KML — no registration needed. Current
  release: World EEZ v12 (2023-10-25).
- Direct download portal: marineregions.org/downloads.php
- Even simpler: a pre-converted, simplified GeoJSON of all countries'
  EEZ boundaries already exists as an open-source dataset:
  **github.com/lsdch/countries-boundaries** — filter this to India's EEZ
  polygon and you have a ready-to-use boundary for geofencing, no
  Shapefile-to-GeoJSON conversion needed.
- **Practical recommendation**: use India's **EEZ boundary** as the
  geofencing reference, rather than chasing the exact bilateral
  International Maritime Boundary Line (IMBL) with Pakistan/Sri
  Lanka/Bangladesh specifically — the IMBL is a precise, treaty-negotiated
  line that's harder to find as clean open data, and India's broader EEZ
  boundary is a legitimate, well-documented, and defensible proxy for "a
  maritime boundary a fishing vessel shouldn't cross" for a prototype.
  This can honestly be described in the pitch as "geofencing against
  India's Exclusive Economic Zone boundary (VLIZ Marine Regions dataset)"
  — a real, sourced, correctly-attributed boundary, not an invented one.

**Implementation note for whoever builds this**: load the EEZ GeoJSON
once at startup (similar pattern to how `marine_data.json` is loaded in
`app/data/loader.py`), use `shapely` to check whether any route waypoint
falls within a threshold distance of the boundary polygon's edge (not
just inside/outside — a route can be worryingly CLOSE to the boundary
without technically crossing it), and surface that as a new field in the
route response for the frontend to render as a warning. Reuse existing
patterns: `services/geocoding.py` already does a similar polygon-adjacent
distance calculation style for `is_near_coast()` — follow that same code
style for consistency.

### 14h. Policy RAG — STEP 2: the actual policy agent, wired end-to-end — DONE (2026-09-15)

Builds on Section 14g's index. Follows the exact same two-file pattern as
route detection/planning: a lightweight, deterministic detection agent
(`policy_detection.py`), then a heavier agent that does the real work
(`policy_agent.py`), chained after it in the graph rather than run as a
same-depth sibling — mirroring `route_detection_node` → `route_planning_node`
exactly, for the same depth-sync reason (Section 6b).

**`app/graph/agents/policy_detection.py`** — `detect_policy_request(query)`
requires BOTH a question-pattern signal (`why`, `explain`, `what does X
mean`, `what is the role/purpose/reason`) AND a policy-domain word (`ban`,
`warning`, `advisory`, `authority`, `ndma`, `imd`, `preparedness`, etc.) -
deliberately a two-part AND, not just "contains why", so an ordinary
live-data question like "why is it windy today" never misfires (neither
"windy" nor "today" is a domain word). `policy_detection_agent` is a thin
wrapper writing `{"policy_request": {...}}` to state, run at the same
graph depth as `route_detection_node` (fed directly by `planner_node`).

**Real bug found and fixed while building this**: a pure policy question
with NO location at all - the task's own example, "why do fishermen need
to return to shore during a cyclone warning" - was falling through to
`planner.py`'s last-resort fallback (`extract_location_phrase` +
`geocode_location`), which strips known stopwords and grabs the LAST
leftover word as a location guess. For this exact query that word is
`warning` (note: `cyclone` is already a stopword in `planner.py`, but
`warning` isn't) - and Open-Meteo's fuzzy geocoding matched it to a real
English village called **Warninglid**, in West Sussex. `is_near_coast()`
would likely have rejected it anyway (all of ORCA's coastal reference
points are in India, ~120km radius), but the user-facing result either
way is a nonsensical location-based error for a question that has nothing
to do with any location - not what "explain a policy" should ever look
like. **Fix**: `detect_policy_request()` is imported directly into
`planner.py` (not just used via its own graph node) and checked
immediately after the known-city-alias loop, BEFORE the fuzzy fallback:
if it's a policy question that didn't already match a known city,
`planner_agent` returns `location_data: None` with **no error at all**,
skipping the fuzzy fallback entirely. **Documented tradeoff**: this means
a policy question naming a real but non-demo coastal town (e.g. "why is
fishing banned near Puri") also won't get its location resolved, since
there's no cheap way to tell "Puri" (a real place) from "warning" (a
policy term) at this point in the pipeline. Favoring safety over
completeness here was a deliberate choice, not an oversight.

**Consequence of "no location, no error" needing to be a valid state**:
previously, every ORCA query either had `location_data` set OR `error`
set - never neither. Introducing a real third state ("no location, this
is fine, it's a policy question") meant `weather_agent`, `ocean_agent`,
`geospatial_agent`, and `risk_agent` all needed a small widened guard
(`if state.get("error") or not state.get("location_data")` /
`or state.get("weather") is None or state.get("ocean") is None` for
`risk_agent` specifically, since it depends on weather+ocean rather than
location_data directly) instead of just `if state.get("error")` - each
now cleanly returns `None` for this case instead of crashing on
`None["lat"]`. `synthesis_agent` got an equivalent new early branch,
mirroring its existing route-request skip: if there's no `location_data`,
it skips the risk-focused Gemini prompt entirely (there's no risk data to
build it from) and just surfaces `policy_agent`'s own answer directly.

**`app/graph/agents/policy_agent.py`** — zero-cost when not needed, same
pattern as `route_planning_agent`: returns `{"policy_answer": None}`
immediately if `policy_request.is_policy_request` is false. Otherwise:
1. Retrieves the top **4** chunks (not 3 - see the district-DMA note
   below) from the Section 14g ChromaDB index via a lazily-loaded,
   cached collection handle (`_get_collection()` - never raises; returns
   `None` if the index is missing or fails to load, same
   return-`None`-on-failure philosophy as `services/weather_api.py`).
2. If nothing retrieved (index unavailable): returns an honest "couldn't
   find anything in the indexed policy documents right now" answer -
   never a fabricated one.
3. If chunks retrieved: builds a prompt that explicitly instructs Gemini
   to answer ONLY from the provided excerpts and to say so honestly if
   they don't actually answer the question, then calls the same
   Gemini endpoint/model/30s-timeout convention as `synthesis_agent`.
4. **Fallback if Gemini fails/unavailable** (rate-limited, no API key,
   timeout - all observed for real in this session, per the known
   pattern in Section 12): returns the raw retrieved chunk text verbatim,
   clearly labeled "this is unprocessed source text, not an AI-written
   answer" - never silently drops the request, matching `synthesis.py`'s
   `_build_fallback_answer` philosophy exactly.
5. Every answer carries a `sources` list (`{title, page, source_url}`,
   deduplicated) so a retrieved answer can always be traced to a real
   document/page.

**Correction to Section 14g's "district DMA" finding**: Step 1's
retrieval test used `n_results=3` and found the district-level DMA
question returned only state/national-level content. `policy_agent` uses
`n_results=4`, and re-testing the SAME query
("what is the role of the district disaster management authority?") at

NDMA/SDMA/**District** Disaster Management Authorities three-tier

specific and correct: DDMA headed by the District Collector/Magistrate,

the earlier test just didn't look far enough down the ranked list. Worth
remembering if a future retrieval-quality issue looks like "missing

**Interaction with normal risk queries - decision and reasoning**: for a
combined query like "why is fishing banned before a cyclone near

pipelines run, independently, and both results are kept** - not merged,
not one overriding the other:
- Chennai resolves via the normal known-city path (this happens BEFORE

| 4 | STOP | 701 | 109 | 810 | full answer |
| 5 | **MAX_TOKENS** | 941 | 79 | **1020** | **cut off mid-sentence** |

**Root cause, definitively confirmed**: `generationConfig.maxOutputTokens`
(1024 at the time) is a budget SHARED between Gemini's hidden "thinking"
tokens and the visible answer text - it is NOT a cap on the visible
answer alone. Even with `thinkingConfig.thinkingLevel` set to `"low"`,
the actual number of thinking tokens spent varied wildly call-to-call for
the exact same prompt - 595 to 941 tokens, a >50% swing with no code or
input change between calls. Both `MAX_TOKENS` attempts show
`thoughts + candidates` landing right at ~1020, just under the old 1024
ceiling - direct proof the shared budget, not the prompt or response
parsing, was the cause. This happened on **2 of 5** real Chennai attempts
in this sample (40%) - a frequent, not rare, failure mode. Chennai was
specifically vulnerable (vs. plainer queries) because its cyclone-alert
reasoning apparently invites more internal "thinking" from the model, but
the underlying bug applies to any query - any prompt could hit an
unlucky high-thinking roll and get truncated the same way.

**Fix**: raised `maxOutputTokens` from `1024` to `2048` in BOTH
`synthesis_agent` (`app/graph/agents/synthesis.py`) and `policy_agent`
(`app/graph/agents/policy_agent.py` - identical `_call_gemini` pattern,
same latent bug, fixed proactively even though it hadn't been reported
there yet). 2048 gives more than 2x headroom over the highest observed
thinking-token usage (941) plus the ~100-150 tokens a full visible answer
actually needs - comfortably absorbing normal thinking variance without
needing to disable or otherwise constrain `thinkingLevel`. This does not
meaningfully change per-call latency, since the model still only *thinks*
as much as it was already thinking - it just no longer gets cut off
before finishing the visible answer when it happens to think for longer.

### 14n. Risk Engine additions: hard-safety override layer + confidence score — DONE (2026-09-17)

Two new PURE, deterministic functions added to `app/core/risk_engine.py`
(no network calls, same style as `calculate_all_metrics`/
`classify_level`), wired into `risk_agent`. Both are built ONLY from
fields ORCA actually has - per this task's own explicit instruction,
neither fabricates a check against an "INCOIS High Wave Red" or "IMD
Orange Warning" feed that doesn't exist; every rule/signal below cites
the real field it's based on.

**1. Government/hard-safety override layer** -
`apply_safety_override(overall_score, overall_level, weather, ocean)`.
Applied AFTER the normal stakeholder-weighted calculation, and can only
ESCALATE the level, never de-escalate it (`_escalate()` always keeps the
more severe of the two). Three rules, each tied to a real field:

| Rule | Real signal | Effect |
|---|---|---|
| Active cyclone alert | `weather['cyclone_alert']` (mock for demo cities like Chennai - Section 4) | Forces **CRITICAL** |
| Very rough sea | `ocean['wave_height_m']` (LIVE, Open-Meteo) ≥ `VERY_ROUGH_SEA_THRESHOLD_M` | Forces at least **HIGH** |
| Lightning detected | `weather['lightning_alert']` (LIVE-derived from Open-Meteo's WMO weather code - Section 4) | Forces at least **MODERATE** |

**The wave threshold was researched, not guessed**: the real, standard
**Douglas Sea Scale** (WMO Sea State Code) defines State 6, "Very Rough",
as **4-6 metres** - confirming the task's own estimate ("I believe very
rough is roughly 4-6m"). `VERY_ROUGH_SEA_THRESHOLD_M = 4.0` uses the
lower bound of that real band, so the override fires as soon as a query
genuinely enters "very rough" territory.

**Design choice, documented in code**: `override_fired` is `True`
whenever a hard-safety CONDITION is true, even if the weighted score had
already independently reached that level or higher - this is deliberate,
so a user can always see "yes, there genuinely is an active cyclone
alert" as a visible fact, not just infer it from the level number never
changing. `apply_safety_override` only returns the escalated LEVEL and
the trigger reasons - it does not touch `overall_score` (which still
reflects the weighted calculation alone) and does not regenerate the
recommendation text; `risk_agent` does that small integration step
itself (re-looking up `RECOMMENDATIONS[stakeholder_type][final_level]`
when the level actually changed), keeping the pure risk-engine function
narrowly scoped to exactly what the task asked for.

**New fields in the risk dict/API response** (all additive):
`overall_level` now reflects the FINAL (possibly escalated) level -
this was a deliberate choice, not an oversight: leaving it at the raw
weighted level while a hard override said otherwise would mean the
frontend badge, the Gemini synthesis prompt, and the recommendation text
all under-state real danger, which would be a genuine safety bug, not
just a missing field. `pre_override_level` preserves what the weighted
calculation alone produced, so nothing is hidden. `override_fired`
(bool) and `override_reasons` (list of strings, empty if nothing fired)
make the override visible and explainable, never silent.

**2. Confidence score** - `calculate_confidence_score(weather, ocean)`,
40% completeness / 30% freshness / 30% agreement, exactly the weighting
given in the task:

- **Completeness (40%)**: fraction of 6 expected fields
  (`wind_speed_kmph`, `wave_height_m`, `sea_surface_temp_c`,
  `salinity_psu`, `current_speed_ms`, `mixed_layer_depth_m`) that are
  non-`None`. Answers "do we have a number to show", not "is it real" -
  `sea_surface_temp_c` counts here even when it's the `DEFAULT_SST_C`
  mock, since a number is still present.
- **Freshness (30%)**: fraction of 5 real, separately-tracked signals
  reporting live - `weather['wind_source'] == 'live'`,
  `ocean['ocean_source'] == 'live'`, and (as an honest proxy, since these
  3 fields have NO mock fallback at all) whether `salinity_psu`,
  `current_speed_ms`, and `mixed_layer_depth_m` each came back non-`None`.
  **Deliberately excludes `sea_surface_temp_c`**: unlike wave height,
  the ocean dict has no separate flag recording whether SST came from
  MOSDAC (live), Open-Meteo (live), or the mock fallback - guessing would
  be dishonest, so it's left out rather than assumed. This is an
  intentional, documented gap, not an oversight.
- **Agreement (30%) - HONEST REINTERPRETATION, explicitly flagged as a
  simplification per the task's own request**: the original idea ("do
  two independent measurements of the same variable agree") doesn't
  apply to ORCA's real data - Open-Meteo and MOSDAC measure DIFFERENT
  variables (wind/wave vs temp/salinity/current/MLD), never the same one
  twice, so there is nothing to literally cross-check numerically.
  Implemented instead as: are BOTH of ORCA's genuinely independent live
  systems (Open-Meteo, MOSDAC) actually up and returning real data this
  call, rather than one succeeding while the other silently falls back?
  Computed as the average of two system-level success fractions -
  Open-Meteo's (wind_source + ocean_source, /2) and MOSDAC's (salinity +
  current + MLD non-None, /3). **Because this is built from the exact
  same underlying source-availability booleans as freshness, the two
  numbers will correlate closely in practice** - that correlation is an
  honest, direct consequence of not having two measurements of the same
  physical variable to compare, not a bug. Documented clearly in the
  function's own docstring so a future reader isn't confused by the
  near-duplication.

**API contract change**: new top-level `confidence` field on every
`/ask` response (`{confidence_score, completeness, freshness,
agreement}`, all additive, `null` when there's no weather/ocean data to
score e.g. the error and pure-policy-question response shapes). New
`risk.pre_override_level` / `risk.override_fired` /

**PART 1 - Route distance sanity check.** `generate_candidate_routes()`
(`route_engine.py`) only does straight-line interpolation + a
perpendicular bend - fine for realistic short trips, but "route from
Kochi to Mumbai" (1067 km) produced a route cutting straight across
Maharashtra/Karnataka's interior, with nonsensical risk scores computed
for waypoints sitting on dry land. **Fix**: a new
`MAX_REALISTIC_ROUTE_DISTANCE_KM = 200.0` constant added to `config.py`,
checked in `route_planning_agent` (`route_planning.py`) via
`haversine_km()` BEFORE `generate_candidate_routes()` is ever called - if
the straight-line distance between origin and destination exceeds it,
`route_planning_agent` returns a `route_plan` with a graceful, honest
`error` message (suggesting the nearest fishing zone or a nearer coastal
town) and zero candidate routes, never a generated route.
**Threshold reasoning, documented in `config.py` itself**: 200 km was
chosen because it already represents roughly a full working day one-way
at this app's own small-fishing-vessel speed assumption
(`estimate_travel_time_minutes()`'s 15 km/h → 200 km takes ~13.3 hours),
well beyond what a small-scale fishing vessel (this app's target user,
per the FAO safety-at-sea document - Section 14m) would realistically
travel point-to-point; beyond it, India's coastline curvature makes
straight-line interpolation genuinely unreliable. Verified live:

### 14t. Route scoring gains the SAME hard-safety override protection as normal risk queries — DONE (2026-09-20)

Section 14s flagged a real gap: route risk scoring never called
`apply_safety_override()` at all, meaning a route through an active
cyclone or genuinely dangerous seas could look merely MODERATE just
because averaging with calmer waypoints elsewhere brought the aggregate
down. This task closes that gap - route scoring now gets the exact same
protection the main Ask ORCA risk agent already has (Section 14n), and
route SELECTION was redesigned so an escalated route can never win just
because its pre-override math looked competitive.

**Backend - override applied per-route, using its own worst waypoint**:
`route_engine.py`'s `score_route()` already identifies each route's worst
scoring sample (Section 5's "a route is only as safe as its most
hazardous point" principle) - it now takes an additional optional
`sample_conditions` parameter (a parallel list of the exact `(weather,
ocean)` dict pairs each sample's `calculate_all_metrics()` call was given)
and attaches the WORST sample's own pair to the route as
`route['worst_sample_weather']`/`route['worst_sample_ocean']`. This keeps
`score_route()`'s own job unchanged (pure aggregation/identification, no
risk computation) - the actual override call happens in
`route_planning_agent` (`route_planning.py`), mirroring `risk_agent`'s own
calling convention exactly: `apply_safety_override(route_risk_score,
pre_override_level, worst_sample_weather, worst_sample_ocean)`, storing
the result as `route['pre_override_level']`/`route['route_risk_level']`
(now the FINAL, possibly-escalated level)/`route['override_fired']`/
`route['override_reasons']` - the identical four-field contract the main
risk response already has, never hidden.

**THE KEY DESIGN DECISION - selection had to become override-aware, not
just label-aware**: simply adding these fields without changing selection
would have been cosmetic only - a route could still get recommended by
`select_recommended_route()`'s existing `combined_score` (risk score +
distance penalty) even after being escalated to CRITICAL, since
`apply_safety_override()` deliberately never touches the raw
`route_risk_score` (Section 14n's own invariant, preserved here). Fixed
by making each route's FINAL `route_risk_level` the PRIMARY sort key
(`_LEVEL_SEVERITY = {"LOW": 0, "MODERATE": 1, "HIGH": 2, "CRITICAL": 3}`,
a new local constant in `route_engine.py` - kept local rather than
imported from `risk_engine.py` so this module's own "pure geometry, no
risk scoring" boundary stays intact, since this is only ranking
pre-computed level LABELS, not computing a risk value), with the existing
`combined_score` used ONLY as a tie-breaker among routes at the SAME
severity tier: `min(scored_routes, key=lambda r: (_LEVEL_SEVERITY[r["route_risk_level"]],
r["combined_score"]))`. A CRITICAL route can now never beat a HIGH-or-
lower route regardless of distance; among routes at the same tier
(e.g. two LOW routes), the existing risk+distance tradeoff still decides
exactly as before Section 14t - no regression to that logic.

**A related honesty fix in `build_route_explanation()`**: since
`route_risk_score` is never touched by the override, comparing raw scores
alone in the deterministic "why this route" text could read backwards -
e.g. "recommended has notably lower marine risk (X vs Y)" when the
shortest (skipped) route's raw score Y might actually be LOWER than the
recommended route's X, if the shortest route was passed over specifically
because of a level escalation, not a raw-score loss. Added a new branch:
when the shortest route was skipped specifically because
`shortest.override_fired` is true AND its final severity exceeds the
recommended route's, the explanation now says so honestly ("X was chosen
instead of the shortest route (Y), which is escalated to {level} by a
hard safety override: {reasons}") instead of comparing numbers that would
otherwise look contradictory.

**API contract change** (`app/api/routes.py`'s `_build_route_field()`):
each candidate route in the `route.candidate_routes` API field now
additionally carries `pre_override_level`/`override_fired`/
`override_reasons`, alongside the existing `route_risk_score`/
`route_risk_level` - additive only, same pattern as every prior route
field addition (boundary/MPA warnings, Section 14o).
