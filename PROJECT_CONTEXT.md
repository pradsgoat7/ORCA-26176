## 1. Problem Statement (SIH26176)

This project is being built for Smart India Hackathon, Problem Statement
26176, sponsored by ISRO (Indian Space Research Organisation), under the
**Disaster Management** theme.

**Title:** ORCA — Marine EcOsystem Reasoning with Collaborative Agents

**Background:** The marine ecosystem plays a vital role in supporting
livelihoods, food security, biodiversity, maritime transportation, coastal
resilience, and the blue economy. Every day, vast volumes of satellite Earth
Observation and oceanographic data (Sea Surface Temperature, chlorophyll
concentration, weather forecasts) are generated by ISRO and other global
agencies. Marine stakeholders (fishermen, researchers, coastal authorities,
disaster management agencies, maritime operators) need timely access to this
information. Advances in Agentic AI, conversational intelligence, and
geospatial technologies present an opportunity to transform how marine
information is accessed.

**Description:** Develop an Agentic AI-powered conversational platform that
lets users access, analyze, and reason over marine information using natural
language. The platform should autonomously interpret user intent, decompose
complex requests into executable tasks, coordinate multiple specialized AI
agents, retrieve relevant marine/geospatial datasets, perform spatial-temporal
reasoning, and synthesize actionable recommendations conversationally.

**Typical user queries the platform must answer:**
- Where is the nearest Potential Fishing Zone (PFZ) today?
- Is it safe to venture into the sea tomorrow morning?
- What are the tide, weather, and sea conditions near my fishing location?
- Are there any lightning or cyclone alerts in my area?
- Which regions show high chlorophyll and favourable SST?
- What is the safest route for a fishing vessel given weather/sea-state?
- Why has fish productivity declined in a particular coastal region?
- Which fishing zones should be avoided due to hazardous conditions or
  geofencing restrictions?

**Expected Solution capabilities (from the official PS):**
- Natural language understanding, multi-turn conversation
- Automatic language identification, responding in the same language
  (emphasis on Indian regional languages)
- Autonomous discovery/retrieval/integration of satellite, marine,
  meteorological, geospatial datasets
- Spatial, temporal, contextual reasoning correlating heterogeneous sources
- Explainable, evidence-based recommendations with maps/charts/visualizations
- Proactive alerts for adverse weather, high waves, lightning, cyclones
- Geofencing notifications near international maritime boundaries,
  restricted waters, marine protected areas
- Route optimization / safe navigation / operational planning
- A modular multi-agent architecture: planning, marine data discovery,
  weather intelligence, ocean analytics, geospatial reasoning, risk
  assessment, visualization, reporting, user interaction agents

## 2. What ORCA Actually Is (Current State)

A working FastAPI + LangGraph backend, with a vanilla HTML/CSS/JS frontend
(a React rebuild is planned but not yet started — see Section 11), that:

1. Takes a natural-language query (typed or spoken) in English, Hindi, or
   Marathi
2. Detects which of 4 stakeholder types is asking (fisherman, coast_guard,
   disaster_management, general) via deterministic keyword scoring
3. Resolves the location (25 known coastal cities with native-script
   aliases, or ANY other city via live geocoding + a coastal-proximity
   sanity check)
4. Fetches LIVE wind, wave, and lightning data (Open-Meteo, free, no API
   key) — with automatic fallback to generic mock values if the live call
   fails
5. Computes 4 individual risk metrics (Wave/Wind/Cyclone/Lightning, each
   0-100) via a **deterministic Risk Engine** — never LLM-generated numbers
6. Combines those into a stakeholder-weighted overall score (0-100) and
   LOW/MODERATE/HIGH/CRITICAL level — different stakeholders get different
   weightings on the SAME underlying conditions
7. If the query is a route request ("find the safest route from X to the
   fishing zone"), generates 3 candidate routes, samples environmental
   conditions along each, scores them via the SAME Risk Engine, and
   recommends the safest one (not necessarily the shortest)
8. Renders a live risk heatmap across all 25 known coastal zones on a
   Leaflet map
9. Uses Gemini (google-generativeai, model `gemini-3.6-flash`) to explain
   the computed numbers in natural language, in the detected language —
   with a fully deterministic multilingual fallback template if Gemini is
   unavailable, rate-limited, or times out
10. Speaks the answer aloud (Web Speech API `speechSynthesis`) in the
    correct language, and accepts spoken input (`SpeechRecognition`)

## 4. Data: What's REAL (Live) vs MOCK — Be Precise About This

This distinction is central to the project's honesty and to the PS's own
data-source requirements. **Never blur this line in code or in the pitch.**

| Field | Status | Source |
|---|---|---|
| Wind speed, precipitation | **LIVE** | Open-Meteo Forecast API (free, no key) |
| Wave height | **LIVE** | Open-Meteo Marine API (free, no key) |
| Lightning alert | **LIVE-DERIVED** | Inferred from Open-Meteo's WMO weather code (95/96/99 = thunderstorm) |
| Sea surface temperature | Live when available, else mock default (28.0°C) | Open-Meteo Marine (not always available as daily forecast) |
| Chlorophyll | **MOCK** (only for 3 "rich" demo cities; `null` for the other 22 + geocoded cities) | No free live API exists for this |
| Cyclone alert | **MOCK** (only Chennai currently has one, `cyclone_alert: true`, for demo purposes) | No free live cyclone-tracking API exists |
| Potential Fishing Zone (PFZ) location | **MOCK** (only for the 3 "rich" demo cities: Kochi, Chennai, Visakhapatnam; `null` for the other 22 + geocoded cities) | INCOIS has NO public API — confirmed via research. Only web bulletins/WebGIS exist, not programmatically accessible |

**The 3 "rich" demo cities** (Kochi, Chennai, Visakhapatnam) have full mock
data (chlorophyll + cyclone + PFZ). **The other 22 cities** in
`marine_data.json` only have real coordinates — everything else is `null`,
and the system HONESTLY says "no PFZ advisory available" rather than
inventing one. **Any other city not in the JSON at all** gets resolved via
live geocoding (Open-Meteo Geocoding API) + a coastal-proximity check
(`is_near_coast`, rejects landlocked results like "Kashmir").

**Day offset / forecast date**: the system correctly parses "today" /
"tomorrow" / "N days later" (English, Hindi, Marathi) and fetches an actual
FORECAST for that day, not just "right now" — this was a real bug we found
and fixed (see Section 8).

## 5. Key Design Decisions — the "WHY", not just the "WHAT"

These are decisions that look arbitrary in the code but were made
deliberately, after discussion. **Do not "simplify" or "fix" these without
understanding why they're this way first.**

1. **Deterministic-first, LLM-explains-only.** The Risk Engine
   (`core/risk_engine.py`) computes every number. Gemini's ONLY job in
   `synthesis.py` is to explain those numbers in natural language — the
   prompt explicitly forbids inventing/changing scores or claiming a
   hazard exists when its metric is 0. This is directly required by the
   spec ("LLM must NOT invent route-risk values").

2. **Fallback-everywhere is load-bearing, not optional polish.** Every
   external call has a graceful degradation path:
   - Live weather/wave fails → generic mock defaults
   - Gemini fails/times out/rate-limited → deterministic multilingual
     template answer (`_build_fallback_answer` in synthesis.py)
   - Geocoding fails → honest "couldn't identify location" error
   This pattern has saved the demo MANY times during development (Gemini's
   free tier rate limits and 30-60s latency spikes were a recurring real
   problem). **Never remove a fallback path to "clean up" code.**

3. **Route risk = MAX of sample scores, not average.** A route is only as
   safe as its most hazardous point along the path, not its average
   condition. This is in `route_engine.py`'s `score_route()`.

4. **Route selection is NOT "shortest wins."** `select_recommended_route()`
   combines risk score with a distance penalty (2 points per extra km
   relative to the shortest candidate) — a longer route can win if it's
   meaningfully safer. This exact weighting was validated against the
   spec's own worked example (17km/risk78 vs 21km/risk24 → 21km route
   correctly wins).

5. **Cyclone risk is binary (0 or 100), never in-between.** There's no free
   live cyclone intensity/tracking API, so rather than inventing a
   plausible-looking intermediate number, the system only ever says
   "active alert" (from mock data) or "no active alert" — no fabricated
   nuance.

6. **Stakeholder-specific weighting genuinely changes outcomes**, not just
   labels. `STAKEHOLDER_WEIGHTS` in `risk_engine.py` — fisherman leans
   wave/wind/cyclone, disaster_management leans cyclone/regional hazard,
   coast_guard is balanced. This was proven to matter: a high-wave/no-cyclone
   scenario landed disaster_management at LOW while everyone else got
   MODERATE — a genuinely different classification, not cosmetic.

7. **Stakeholder detection is keyword-based, not an LLM call.** Deliberately
   deterministic (free, instant, doesn't compete with Gemini's rate limit).
   Same for route-request detection.

8. **PFZ reuse for route destinations.** When a route request mentions "the
   fishing zone" / PFZ, the destination is the ALREADY-KNOWN `nearest_pfz`
   from `marine_data.json` for the resolved origin city — never a second,
   separate data source. If no PFZ exists for that city, the route request
   fails gracefully with an honest message, per the spec's explicit "do
   not invent coordinates" rule.

## 6. Known Bug Classes — Patterns to Watch For

These bugs were each found and fixed once already. **Watch for these exact
patterns recurring**, especially the LangGraph ones, since they're subtle.

### 6a. LangGraph "must write to at least one key"
A node CANNOT return an empty dict `{}`, even when it has nothing to
contribute (e.g., short-circuiting on an error). Every node must return
`{"some_key": None}` — writing `None` to its OWN unique key — never `{}`.

### 6b. LangGraph depth-synchronization race condition (hit 3 times)
If two parallel branches feed into a shared downstream "barrier" node, and
those branches are at DIFFERENT depths from a common ancestor (one is 1 hop
away, the other is 2 hops away), the barrier node can fire prematurely —
before the deeper branch has finished — causing a `KeyError` on missing
state. **The fix is always the same: restructure the graph so every branch
feeding a shared barrier node is at the exact same depth.** Look at
`workflow.py`'s comments for the current correct topology
(`route_planning_node` specifically had to be re-routed through
`route_detection_node` rather than being a direct sibling, for exactly
this reason).

### 6c. LangGraph concurrent-write conflict
Two parallel nodes writing to the SAME state key in the same step raises an
error, even if the values are identical. Fix: never use
`return {**state, "new_key": value}` in a node that might run in parallel
with others — only return the NEW key(s) that specific node is adding.

### 6d. Python `from X import Y` creates a separate binding
If module `weather.py` does `from app.services.weather_api import
fetch_live_wind`, then mocking `app.services.weather_api.fetch_live_wind`
in a test will NOT affect what `weather.py` actually calls — you must
patch `app.graph.agents.weather.fetch_live_wind` (the importing module),
not the source module. See `tests/test_phase7.py` Test 4 for the correct
pattern.

### 6e. Regex without word boundaries
A location-extraction regex looking for "at X" matched the "at" inside
"wh**at** about mumbai", extracting the wrong word. Fixed with `\b`
boundaries. **Always use word boundaries in location/keyword regexes.**

### 6f. Fuzzy geocoding can return wildly wrong results
Open-Meteo's geocoding does fuzzy text search, not exact matching —
nonsense input like "hii" once matched a real place called "Lake Havasu
City". Fixed with a prefix-match sanity check (`geocode_location()` in
`geocoding.py`) rejecting results where the first few letters don't match
the input.

### 6g. File casing on case-sensitive filesystems
`Script.js`/`Style.css` (capitalized) vs `index.html` referencing lowercase
`script.js`/`style.css` — silently worked on macOS (case-insensitive) but
would 404 on Linux. **Always use lowercase filenames consistently.**

### 6h. Mock coordinate drift
Visakhapatnam's PFZ coordinate was originally offset both north AND east
from the city, which (given the coastline's actual curve there) placed it
very close to/on land when drawn precisely on a map. Fixed by using a
same-latitude, due-east offset instead — a more reliable heuristic for
staying in open water on an east-facing coast. **Any new mock coordinate
should be sanity-checked by actually drawing it on a map, not just
eyeballing the lat/lon numbers.**

## 7. Testing Philosophy (established over the whole project)

- **Never trust "it should work" — always execute it.** Every feature in
  this project was verified by actually running it (real function calls,
  real FastAPI TestClient requests, or realistic mocked data), not just
  code review.
- **For JS, browsers share top-level `const`/`let` across separate
  `<script>` tags — Node's `eval()` does NOT.** When testing multiple JS
  files together outside a real browser, concatenate them into one string
  and `eval()` that as a single unit, matching real browser semantics,
  rather than `eval()`-ing each file separately in a loop.
- **When mocking a live API failure, actually simulate the failure mode**
  you're protecting against (e.g., a promise that never resolves for a
  "hang" test, not just a rejected promise — those are different failure
  modes requiring different protections).
- Run `python3 -m tests.test_phase7` after ANY change to confirm the 6
  core scenarios (fisherman/coast_guard/disaster_management/high-risk
  fisherman/Hindi/Marathi) still pass — this is the fastest regression
  check available.

## 9. Current API Contract

### `GET /`
Health check. Returns `{"status": "ORCA backend is running"}`.

### `GET /zones?stakeholder=<type>`
Returns risk for all 25 known coastal zones, computed in parallel via a
thread pool (25 zones × 2 live API calls each = 50 calls; sequential would
be too slow). `stakeholder` defaults to `"general"`.
```json
{
  "zones": [
    {"name": "Kochi", "lat": ..., "lon": ..., "overall_score": 19,
     "overall_level": "LOW", "primary_driver": "Wave Risk",
     "wave_height_m": ..., "wind_speed_kmph": ..., "recommendation": "...",
     "data_source": "live", "has_data": true}
  ],
  "legend": {"LOW": "🟢", "MODERATE": "🟡", "HIGH": "🟠", "CRITICAL": "🔴"}
}
```

### `POST /ask`
Body: `{"query": "..."}`. Response (success case):
```json
{
  "answer": "...",
  "language": "en",
  "risk_level": "safe",              // legacy field, kept for compatibility
  "risk_reasons": ["..."],           // legacy field
  "weather": {...}, "ocean": {...},
  "map": {"user_location": {...}, "location_name": "...", "nearest_pfz": {...} or null},
  "stakeholder": {"type": "fisherman", "confidence": 0.85},
  "risk": {
    "overall_score": 19, "overall_level": "LOW",
    "metrics": [{"name": "Wave Risk", "key": "wave_risk", "score": 45}, ...],
    "reasons": [{"factor": "Wave", "score": 45, "reason": "..."}],
    "recommendation": "..."
  },
  "route": null  // or a full route object if this was a route request - see routes.py
}
```
On error (`result.get("error")` truthy — e.g., unresolvable location):
`{"answer": ..., "error": "...", "stakeholder": {...}, "language": "en", "risk": null, "route": null}`

**Important**: the `route` field is present (non-null) whenever the query
was a route request, REGARDLESS of whether the top-level `error` field is
also set — this was a real bug we fixed (route-specific errors were being
silently dropped by the generic error branch).

## 13. RESEARCH FINDINGS: MOSDAC + Maritime Boundary Data (verified via direct web fetch)

### 14a. MOSDAC Data Download API — genuinely more complex than a simple REST API

**Verified directly from MOSDAC's own published user manual**
(mosdac.gov.in/downloadapi-manual). Key facts:

- It is a **file-download tool**, not a point-query API like Open-Meteo.
  You provide a `config.json` with a `datasetId` (e.g., `"3SIMG_L1B_STD"`,
  found by browsing mosdac.gov.in/catalog-app/satellite), an optional
  `boundingBox` (format: `"minLon,minLat,maxLon,maxLat"`), date range,
  and count — then run `python mdapi.py`, which downloads matching
  **satellite scene files** (likely NetCDF/HDF5 format, based on typical
  ISRO satellite product formats — not directly confirmed in the manual,
  needs checking once a specific product is chosen).
- **This means getting a single SST or chlorophyll VALUE at one lat/lon
  point requires: (1) finding the right datasetId for that product,
  (2) downloading a full scene file covering that area, (3) parsing that
  file with something like `xarray`/`h5py`/`netCDF4` to extract the pixel
  value at your specific coordinate.** This is a real geospatial data
  engineering task, not a quick API call — realistically 1-2+ days of
  work just to get ONE working extraction pipeline, even before dealing
  with real-time freshness (satellite revisit time, file availability
  lag).
- **Authentication**: searching/browsing datasets needs NO login; only
  actual file DOWNLOAD requires a MOSDAC account. Register at
  mosdac.gov.in/signup/ — approval is required before downloading (this
  is why registering EARLY, on Day 1-2, matters).
- **Quotas**: 5000 files/day/user (not a bottleneck for a demo). 3 failed
  logins in a row = 1 hour account lockout (be careful with credentials
  in scripts/config files during testing).
- Relevant ocean product categories that exist on MOSDAC's Open Data page
  (confirmed real, though exact datasetIds need to be looked up in their
  catalog): Global Ocean Surface Current, High Resolution Sea Surface
  Salinity, Indian Mainland Coastal Product, Ocean Subsurface, Oceanic
  Eddies Detection, Wave based Renewable Energy.

**Recommendation for the 10-day plan**: attempt this with a **strict
1-day time-box**. If a working point-value extraction isn't functioning
by the end of Day 3, STOP and use NASA Ocean Color
(oceancolor.gsfc.nasa.gov) or Copernicus Marine
(data.marine.copernicus.eu) instead — both are still genuinely real,
public, free ocean data sources (just not ISRO-branded), and both
generally offer more developer-friendly access than a raw satellite-file
archive. A working non-ISRO real data source beats a broken or
half-finished ISRO one. Be honest in the pitch either way about exactly
which parts are ISRO-sourced vs. not.

### 14b. Maritime boundary / geofencing data — actually LOWER risk than assumed

**Good news, verified via direct research**: getting real, usable
maritime boundary data is much easier than the MOSDAC situation.

- **Marine Regions** (marineregions.org), maintained by VLIZ (Flanders
  Marine Institute) in partnership with IOC-UNESCO, is the standard
  authoritative source for Exclusive Economic Zone (EEZ) boundaries
  worldwide. **All data is free, open-licensed, and downloadable** as
  Shapefile, GeoJSON, GeoPackage, or KML — no registration needed. Current
  release: World EEZ v12 (2023-10-25).
- Direct download portal: marineregions.org/downloads.php
- Even simpler: a pre-converted, simplified GeoJSON of all countries'
  EEZ boundaries already exists as an open-source dataset:
  **github.com/lsdch/countries-boundaries** — filter this to India's EEZ
  polygon and you have a ready-to-use boundary for geofencing, no
  Shapefile-to-GeoJSON conversion needed.
- **Practical recommendation**: use India's **EEZ boundary** as the
  geofencing reference, rather than chasing the exact bilateral
  International Maritime Boundary Line (IMBL) with Pakistan/Sri
  Lanka/Bangladesh specifically — the IMBL is a precise, treaty-negotiated
  line that's harder to find as clean open data, and India's broader EEZ
  boundary is a legitimate, well-documented, and defensible proxy for "a
  maritime boundary a fishing vessel shouldn't cross" for a prototype.
  This can honestly be described in the pitch as "geofencing against
  India's Exclusive Economic Zone boundary (VLIZ Marine Regions dataset)"
  — a real, sourced, correctly-attributed boundary, not an invented one.

**Implementation note for whoever builds this**: load the EEZ GeoJSON
once at startup (similar pattern to how `marine_data.json` is loaded in
`app/data/loader.py`), use `shapely` to check whether any route waypoint
falls within a threshold distance of the boundary polygon's edge (not
just inside/outside — a route can be worryingly CLOSE to the boundary
without technically crossing it), and surface that as a new field in the
route response for the frontend to render as a warning. Reuse existing
patterns: `services/geocoding.py` already does a similar polygon-adjacent
distance calculation style for `is_near_coast()` — follow that same code
style for consistency.
